## 1. `DataVersion`：三把"要不要同步"的尺子里，两把刻度永远停在 0

`common/ha/DataVersion.java:6-9` 的 javadoc 主张（逐字）：

> Master 在每次更新 TopicConfig / ConsumerOffset / DelayOffset / SubscriptionGroup 时递增版本号.
> Slave 通过对比本地 DataVersion 与 Master 的 DataVersion 决定是否需要同步, 实现增量同步.

实测（`grep -rn --include='*.java' "assignNewVersion" */src | wc -l` = **14**，其中 `*/src/main` **3** 行、`*/src/test` **11** 行）：
`src/main` 那 3 行 = 声明本身（`DataVersion.java:32`）+ 同一个对象的两次调用：

```
z-mq-broker/.../processor/AdminBrokerProcessor.java:96   topicConfigDataVersion.assignNewVersion();
z-mq-broker/.../processor/AdminBrokerProcessor.java:145  topicConfigDataVersion.assignNewVersion();
```

（test 那 11 行 = `TopicConfigWiringGuardTest:55` 的字符串常量 1 + `DataVersionTest` 的 10，都不改变"谁被递增"这个事实。）⇒

- `BrokerController.java:123 consumerOffsetDataVersion` / `:124 delayOffsetDataVersion`：
  只被 `:540/:547` 两个 getter 和 `BrokerOutAPI.java:97/111/130/131` 读出去 ⇒ **counter 恒 0，timestamp 恒等于构造时刻**
  （`DataVersion:23` 在 new 时取一次 `System.currentTimeMillis()`，之后没有任何路径会更新它）。
- **判定侧真的在读它**：`SlaveSynchronize.java:167/203/248` 三处
  `if (!wrapper.getDataVersion().isNewerThan(local…Version)) return;`，
  而 `DataVersion.isNewerThan:60-63` 在 counter 相等时**退化成比 timestamp**。
  consumerOffset / delayOffset 两侧的 counter 恒等 0 ⇒ 这一票到底同步不同步，取决于两个构造时刻谁先谁后。
- **不落盘**：三处版本对象都是 `new DataVersion()`（`BrokerController:123/124`、`SlaveSynchronize:61/63/65`、
  `AdminBrokerProcessor:46`），`grep -rn --include='*.java' "dataVersion" z-mq-store/src/main/java` = **0 命中**
  （加 `-i` 做大小写不敏感仍是 **0**），`TopicConfigManager.persist()`（`:235-252`）逐条写 `TopicConfig` 的 JSON，
  整份文件里没有版本号的位子。
  ⇒ master 重启 ⇒ `AdminBrokerProcessor` 重建 ⇒ counter 归 0，而 slave 本地那份还停在重启前从 master 抄来的值
  （`SlaveSynchronize:180-181`），于是 `isNewerThan` 判假 ⇒ **topic 配置同步在 master 重启后长期被跳过**。

判这块时不要把我的话当尺，命令在上一段里，逐条能复跑。

**等排产决定**：这三条（补齐 bump / 版本号进盘 / `isNewerThan` 的退化分支）是并入 **W5e（HA 复制的数据面）**，
还是单立一张 W2i？我倾向并入 W5e——它和 `slaveAckOffset` 是同一条因果链上的东西（都是"slave 报回来的数没有真值"）。

## 2. `DELETE_TOPIC` 有码无处理器、无发送方，所以 topic 只增不减

`grep -rn --include='*.java' "DELETE_TOPIC\|removeTopic\|deleteTopic" .` 全树 **2 行**：

```
z-mq-remoting/.../protocol/RequestCode.java:44   public static final int DELETE_TOPIC = 7;
z-mq-broker/.../slave/SlaveSynchronize.java:28    *   <li>TopicConfig — …(createTopic/updateTopic/deleteTopic)</li>
```

第二行是注释里的第三个词。⇒ 没有处理器分支（`BrokerController` 注册的 11 条里没有它，尺：
`grep -A1 "this\.remotingServer\.registerProcessor(" …/BrokerController.java | grep -o "RequestCode\.[A-Z_]*"`
⇒ `SEND_MESSAGE PULL_MESSAGE UPDATE_AND_CREATE_TOPIC UPDATE_CONSUMER_OFFSET GET_ALL_TOPIC_LIST GET_ALL_TOPIC_CONFIG
GET_ALL_CONSUMER_OFFSET GET_ALL_DELAY_OFFSET GET_ALL_SUBSCRIPTION_GROUP QUERY_DATA_VERSION HA_REPORT_OFFSET`），
`TopicConfigManager` 的 public 面（`:90 putTopicConfig / :110 replaceAllTopicConfigs / :134 selectTopicConfig /
:144 getAllTopicConfigs / :151 size / :156 clear / :169 flush / :181 shutdown`）里**没有单个 topic 的删除口**，
只有 `clear()`——而 `clear()` 在 `src/main` **零调用者**（阳性对照：同类里 `persist()` 有 4 个调用点 `:97/:125/:160/:172`）。

**README 里没有"删除 topic"的广告**（尺：`grep -niE "删除.{0,6}topic|delete.{0,6}topic" README.md | wc -l` = **0**；
同一条尺拿 README:117 那句「Master-Slave 同步双写」当阳性对照，用 `grep -n "Master-Slave" README.md` 出 1 行），
所以这一格不是广告缺口，是协议表里的空号。

**等排产决定**：补 `DELETE_TOPIC`（含"删除后落盘、重启不复活"的验收），还是把 `RequestCode.java:44` 标注为保留码？
补的话写域与 W2d 完全重叠（`TopicConfigManager` + `AdminBrokerProcessor`），我建议排在 W2e/W2f 收口之后、和 W2h 一并做。
