
⇒ 两条后果，都量得出来：① 半消息实际由 `SendMessageProcessor` 当**普通消息**落住（事务处理器压根看不到它），
`processHalfMessage` 那一半今天**不在请求路径上**；② commit/rollback 那条 251 **必然失败**。
③ 还有 key 问题：`:81` 已经把 topic 改掉了，"提交后投回原 topic"需要 `ORIGINAL_TOPIC`，而它今天只在没人构造的那个处理器里写。

## 3. 为什么"回查"这一半是架构问题，不是接线问题

- `TransactionCheckService:105` 调的是**同 JVM 内**的 `checkCallback.checkTransaction(...)`；
- broker 要"回查"必须**反向连到 producer**，而 `grep -rn NettyRemotingServer --include=*.java z-mq-client/src/main` = **0**
  ⇒ client 进程没有监听端口，broker 在网络上到不了它。
- `CHECK_TRANSACTION_STATE`(250) 这个码的方向正是 broker→client，**当前拓扑下不可能被送达**。

⇒ 只有两种可兑现形状，**都要用户拍**：
 (a) producer **主动拉**（client 定时问 broker"有没有待回查的"，把 250 变成 client 发起的查询）；
 (b) broker **进程内驱动** + 事务状态**落盘**（回查只在同 JVM 的 producer 实例上有效，跨进程不支持并写进文档）。
**别照 RocketMQ 的形状假设它接得上**——它的前提是 client 侧也有可连的端点，本仓没有。
