# feature008：位点提交点是**整批**判的，一条没后继就拖着全批重拉

登记时间：2026-09-27 00:2x（行号、引文均为当场从盘上读，不是转述）

## 这事是什么

`DefaultMQPushConsumer.handleConsumeFailure`（`z-mq-client/src/main/java/com/zifang/z/mq/client/consumer/DefaultMQPushConsumer.java:356-374`）
把"要不要提交这一批的位点"判在**整批**层面：

```java
boolean allPersisted = true;
for (MessageExt msg : messages) {
    int outcome = consumeRetryService.addRetryMessageForOutcome(msg, reconsumeTimes);
    if (outcome != ConsumeRetryService.OUTCOME_RETRY_PERSISTED
            && outcome != ConsumeRetryService.OUTCOME_DEAD_LETTER_PERSISTED) {
        allPersisted = false;
    }
}
if (allPersisted) {
    commitOffsetThrough(brokerAddr, mq, nextOffset);
}
```

后果的形状：批里只要有一条走 `OUTCOME_IN_PROCESS_RETRY` 或 `OUTCOME_DEAD_LETTER_CACHED`（进程内才有真相，
提交就丢），**整批**都不提交 ⇒ 那些已经拿到 `OUTCOME_RETRY_PERSISTED` 的消息会被再拉一次，
再拉一次就**再多落一份重投副本**（`ConsumeRetryService.addRetryMessageForOutcome:265-283`：落盘成功就直接 return，
副本的 msgId 是 `原id#R{级数}`，级数由消息字段自己带着，所以每一份都是新的一行）。

W2e-R 已经堵掉了同一分支上的另一头（死信记账的自重复：`DeadLetterQueue` 现在对 `(topic, msgId, 级数)` 幂等，
见 `DeadLetterQueueIdempotencyTest`），**这一头没堵、也不该由那一支堵**：这里重复的是重投副本，不是死信记账。

## 等主编/用户拍什么

1. **提交点粒度要不要从"整批"改成"逐条"**：改成逐条就要能按消息提交位点，
   而这里的位点是 `payload.getNextOffset()`（一个队列上的**单调游标**），逐条提交在结构上不成立 ——
   要么改成"按批内最靠前的、其后继全部已落盘的前缀"提交（prefix commit），要么维持整批判定并接受重拉放大。
2. 如果维持整批判定，要不要在 README/javadoc 里把"失败批次的重复投递代价"说清楚
   （现在广告的是 at-least-once，语义上没错，但没说"同批邻居会连带重投"）。
3. 派产归属：拍完第 1 条之后，这件事要单独一支（碰 `DefaultMQPushConsumer` 的提交点，
   W2e/W2e-R 明确把它划成禁区，不许顺手改）。
