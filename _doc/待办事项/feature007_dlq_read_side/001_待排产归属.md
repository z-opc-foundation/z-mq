# feature007 · 死信的"批量取走侧"仍然零读者（等排产归属，不等拍板）

登记时间：**09-26 23:53–23:55**（`date` 现读）。实测树：**`b8989d7`**（分支 `w2e`）。

## 一句话

W2e 把死信的**投递**侧接上了（发到 `%DLQ%{group}`，别的消费者能 pull 到），但**进程内那个死信缓存**
仍然只有入口没有出口：`pollAll()` 在 `src/main` 里没有任何读者。守卫用例已经能机检这件事，
所以这不是"没发现"，是**发现了并留着等归属**——它要的是一个人工处理/重放的入口，那是工具面的设计，不该由消费端顺手拍。

**这条读数同时是 `DeadLetterQueueReaderGuardTest` 现在为什么不红的原因**：守卫的判据是
"取走侧（`pollAll` **或** `getDlqTopic`）至少 1 个读者"，W2e 给 `getDlqTopic()` 补上了读者
（`DefaultMQPushConsumer.getDeadLetterTopic()`），于是守卫绿了，而 `pollAll` 至今 0 读者——
**守卫 satisfying 的路径和"人工处理闭环"不是同一件事**，这一点必须写下来，不然下一个人会以为闭环已完成。

## 归属建议（不替 W4 拍设计）

- 建议挂 **W4 工具面**：`z-mq-tools` 里一个"列出/导出/重放某消费组死信"的口，或者干脆只认
  "死信 Topic 由另一个消费者订阅"这一条通路，把进程内缓存降级为纯统计（那就要删 `pollAll`，与本仓
  "不删广告"的裁定无关——`pollAll` 从没在 README 广告过，删它不算删广告，算删摆设）。
- 两个方向**都能收掉这条账**，区别是"进程内那份缓存到底算不算一个可运维的东西"。
  这条等下一次盘 W4 时一起定，不必单独打断战役。

## 如果选"删摆设"，注意

`getTotalDeadLetters()` / `getTotalExpired()` 目前也只有测试读者（W2e 那棒的 §1.2 实测过一轮：
五个取走侧符号全是声明行）。删 `pollAll` 时要一起看这两个计数要不要留——**统计数如果有读者（控制台/Prometheus），
它就是广告面**；如果没读者，那它和 `pollAll` 是同一种摆设，别只删一半留一半更迷惑。
