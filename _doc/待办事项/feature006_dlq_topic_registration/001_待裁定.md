# feature006 · 死信要落到 `%DLQ%{group}`，还差"这个 topic 谁注册"这一步（等拍板）

登记时间：**09-26 23:53–23:55**（`date` 现读，非推算）。
实测树：**`b8989d7`**（分支 `w2e`，= W2e 本体 + 我删的 `lastSentTimes`）；复跑命令里的 `<rev>` 一律现场取，别抄本文编号。

## 一句话

README:120 那句 `✅ Consumer 消费失败重投（最多 16 次，超过进死信队列）` 的**投递**这一环 W2e 已经接上
（副本走真 `SEND_MESSAGE`，另一个消费者能从 `%DLQ%{group}` pull 到），但**死信 Topic 本身仍要靠显式一步注册**
——产品侧没有任何自动登记，所以真实应用**第一次**转入死信时大概率量不到路由，走的是进程内兜底那一路。

## 实测（全部在 `b8989d7` 上）

| 主张 | 命令 | 读数 |
| --- | --- | --- |
| client 模块没有任何建 topic 的入口 | `git grep -n "UPDATE_AND_CREATE_TOPIC" <rev> -- "z-mq-client/*"` | **0 命中** |
| 这个请求码本身不是空号（尺活着） | `git grep -c "UPDATE_AND_CREATE_TOPIC" <rev> -- "*/src/main/*"` | **5 个文件**（`AdminBrokerProcessor` / `BrokerController` / nameserver `DefaultRequestProcessor`×4 / `RequestCode`×2 / `z-mq-tools` 的 `ClusterAdmin`）⇒ 唯一会建的是**管理侧**，不是消费侧 |
| broker 发送侧不自动建 topic | `git grep -niE "autocreate\|createTopicIfAbsent" <rev> -- "*/src/main/*"` | **0 命中**（阳性对照：`git grep -niE "topicConfigTable\|getTopicConfig" <rev> -- "*/src/main/*" \| wc -l` = **30** ⇒ 扫的是活树，不是空扫） |
| 写手自己也是这么测的 | `w2e` 那一棒在 E2E 里显式 `registerTopic(dlqTopic)`，并在"没注册"那一例断言 `routeAbsent(...)` 前后都成立 | 见 `RetryDeadLetterE2ETest:220-224 / 284-286 / 311` |

⇒ 也就是说：**"订阅死信 Topic 做人工处理或告警"这句话，今天要求运维先替每个消费组把 `%DLQ%{group}` 建出来**，
否则死信投不出去、只留在进程内缓存里（那一路的另一条缺陷见战役卡 W2e 审计一节：重拉下会被自己的副本挤掉）。

## 等拍板的三选一（我不替产品拍）

1. **broker 侧自动登记**：`SEND_MESSAGE` 命中 `%DLQ%*`（或首次心跳）时按默认队列数登记一份。
   代价：改变"broker 不自动建 topic"这条既有边界，且要给 `%DLQ%*` 一个特例规则——这条规则一旦广告出去，
   就要钉"为什么只有死信前缀享受特例"。
2. **client 侧启动时登记**：`installDurableRetryPaths()` 顺手为本组死信 Topic 发一次 `UPDATE_AND_CREATE_TOPIC`。
   代价：把管理请求码接进消费端（正是上面 0 命中那条账要翻转的地方），权限面从"运维建 topic"变成"任何消费者能建"。
3. **不做，诚实化**：README 那句改成"死信 Topic 需预先注册（`z-mq-tools` 的 admin 口）"，并在 starter 文档里给一条命令。
   代价：这是**删广告式**修法，而用户 09-26 对八件事的裁定是"一件都不删、全部补实现" ⇒ **选这条要先单独点头**。

**我的倾向**：走 1，并把特例规则钉成"只认 `DLQ_TOPIC_PREFIX` 前缀 + 只由 broker 在收到该前缀发送时登记 + 队列数取自配置"。
理由：它是三选一里唯一让 ✅ 那句在无运维动作下真的成立、且不放宽普通 topic 语义的做法。但这条改了 broker 的建表边界，
**不在 W2 的票里，属于要单独拍板的范围扩张**。
