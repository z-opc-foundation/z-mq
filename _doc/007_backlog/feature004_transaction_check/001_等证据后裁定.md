## 3. 为什么"回查"这一半是架构问题，不是接线问题

- `TransactionCheckService:105` 调的是**同 JVM 内**的 `checkCallback.checkTransaction(...)`；
- broker 要"回查"必须**反向连到 producer**，而 `grep -rn NettyRemotingServer --include=*.java z-mq-client/src/main` = **0**
  ⇒ client 进程没有监听端口，broker 在网络上到不了它。
- `CHECK_TRANSACTION_STATE`(250) 这个码的方向正是 broker→client，**当前拓扑下不可能被送达**。

⇒ 只有两种可兑现形状，**都要用户拍**：
 (a) producer **主动拉**（client 定时问 broker"有没有待回查的"，把 250 变成 client 发起的查询）；
 (b) broker **进程内驱动** + 事务状态**落盘**（回查只在同 JVM 的 producer 实例上有效，跨进程不支持并写进文档）。
**别照 RocketMQ 的形状假设它接得上**——它的前提是 client 侧也有可连的端点，本仓没有。

### 5.3 本支量出来的三个新缺口（都要裁定，不属"接线"）

1. **掉电窗口是"二次投递"方向**：`resolveTransaction` 的顺序是 `commitTransaction`(`:241`) →
   `reDeliverToOriginalTopic`(`:246`) → `appendResolveRecord`(`:251`)。若进程在 `:246` 与 `:251`
   之间死掉：消息已经在原始 topic 上，但盘上没有定论记录 ⇒ 重启重放把这条半消息**收回待回查集合**，
   下一轮回查再 COMMIT 就是第二份。反向修法（先记账再回投）会把方向换成"丢消息"，
   所以真正要选的是"要不要在拉取侧按 transactionId 去重"——这是架构裁定，不是补一行。
   现有用例覆盖的是"两步都落完"的 `committedTransactionIsNotPutBackIntoThePendingSetAfterRestart`，
   **中间那个窗口没有任何测试能构造**（没有注入点）。
2. **250 的清单不分页**：`getPendingTransactions()`（受 `checkIntervalMillis` 门控，`:279`）与
   `listAllPendingTransactions()`（不受门控，`:292`）都是整份 `List` 直接 `JsonCodec.encode` 进响应体。
   待回查堆积时响应无界，而 producer 每一次拉取都要整份反序列化。
3. **`halfBrokerAddrTable` 只在进程内存里**：它记录"这条事务的半消息落在哪个 broker"，重启后为空 ⇒
   多 broker 部署下，producer 重启后对旧事务的 251 提交会找不到 broker 地址（本支测试是单 broker，量不到）。
